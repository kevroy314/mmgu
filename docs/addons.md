# Add-ons

Add-ons are optional parts of the hall that are **off until a leader turns them on**. Three ship with
Hallkeeper:

| Add-on | What it does | Game terms risk |
|---|---|---|
| **Screenshot Reader** · AI item reading | A vision model reads item and bank screenshots and fills in the form | Check the terms |
| **Ledger Sync** · import from game log files | Receives loot and kills from a script members run on their own PC | High |
| **Claude Integration** · MCP server | Lets Claude look things up in the hall and suggest changes | None (only the hall's own data) |

## Turning one on

Steward's Office → **Add-ons**. Add-ons that may run into the game's terms show a notice; a leader has
to read it and tick the box before the add-on opens. The hall records who accepted it and when in the
audit log. Turning an add-on off hides its pages and stops it immediately; its data stays.

Settings (models, API keys and so on) appear in Steward's Office → **Settings** once the add-on is on.

## Where the line is

Monsters & Memories' user agreement prohibits unauthorized software that "intercepts, collects, reads, or
mines" information generated by the game, and its Play Nice Policy bans bots and automation. The
developers may loosen this. Hallkeeper's position (more in [terms-of-service.md](terms-of-service.md)):

- **The core hall never touches the game.** It stores what people type or upload by choice.
- **Anything that reads game output is an add-on with a plain notice**: screenshots (Screenshot Reader),
  or events sent by a companion script (Ledger Sync). Using them is each guild's decision.
- **Companion scripts run on a player's own PC** and ask that player first. Running one is that
  player's decision and responsibility.
- **Never**: reading game memory, intercepting network traffic, injecting input or automating play.

Everything a machine produces (a screenshot read, an imported unknown item, a Claude suggestion) waits as a
suggestion until a person approves it.

## Screenshot Reader

Adds **Read a screenshot** to the Archive's *Catalog an item* page, and a bank-screenshot reader the Vault
can use. The model's answer only pre-fills the form; a person checks it and presses Save.

- **Ollama (default)**: runs a vision model on your own hardware, free and private. The default is
  `qwen3-vl:8b` (about 6 GB; fits an 11 GB GPU). With the bundled Docker profile:
  `docker compose --profile ai up -d`, then pull the model once. Settings: *Ollama address*
  (default `MMGU_OLLAMA_URL` or `http://localhost:11434`) and *Ollama model*.
- **Claude (optional)**: set *Which model reads screenshots* to `anthropic` and add an API key (or set
  `ANTHROPIC_API_KEY`). Default model `claude-haiku-4-5`. Each read is a paid API call.

How it reads: the model gets the screenshot, a prompt describing an EverQuest-style inspect window, and a
JSON Schema built from the game pack (slots, flags, stats, resists, skills, classes). It transcribes the
window first, then fills in the fields; anything it leaves empty is filled by parsing its own transcript
("STR: +2", "Slot: PRIMARY"...). The Archive then normalises names and classes against the game pack.
Doubts are shown on the form, e.g. "Class names not in the game pack: WAR".

Speed on a GTX 1080 Ti with `qwen3-vl:8b`: about 16 seconds per item window once the model is loaded,
30+ seconds for the first read after it has been idle. `qwen3-vl` is a "thinking" model and Ollama 0.35
doesn't switch its thinking off when asked, which made a read take over two minutes; the reader skips it
by starting the answer with an empty think block. Turn on *Let the Ollama model think* to allow it anyway.

Leaders get a page at **/addons/screenshot-reader** with *Check connection* (lists the models Ollama has)
and *Test the reader* (upload a screenshot, see the raw JSON and the fields the form would get; nothing is
saved). Use it when trying another model.

Tips for members: crop to the item window. Small, sharp text reads much better than a whole 4K screen
(images are shrunk to 1600 px on the long side).

## Ledger Sync

The game keeps a local activity log, the **Ledger**: JSON files under
`%USERPROFILE%\AppData\LocalLow\Niche Worlds Cult\Monsters and Memories\<server>\<Character>\Ledger\`.
Members who choose to run [`companion/ledger_sync.py`](../companion/README.md) send the relevant events to
the hall:

- **Loot** (`act_13`) of an item the Archive knows → a drop report with source "ledger". An unknown item →
  one suggestion per item name for someone to review (setting: *Suggest new Archive items for unknown loot*).
- **Kills** (`act_14`) of creatures the Watch tracks → a time of death on that timer (only the latest kill per
  creature in an upload, and only kills newer than *Ignore kills older than*, default 72 hours).
- **Vendor sales** (`act_24`) and **harvests** (`act_27`) are counted and otherwise ignored for now.

The endpoint is `POST /api/addons/ledger/events` with a personal API token (`Authorization: Bearer mmgu_...`)
and the *Catalog items and report drops* permission:

```json
{"character": "Lyra", "server": "Oakvale",
 "events": [{"type": "loot", "at": "2026-09-30T21:04:11Z", "item": "Rusty Scimitar",
             "creature": "a bandit", "zone": "Scarwood", "qty": null, "raw": {"event_id": "..."}}]}
```

`type` is `loot`, `kill`, `vendor_sale` or `harvest`; at most 1,000 events per request. Each event is
hashed (from `raw.event_id` when present, otherwise from its fields) and imported once; sending it again
does nothing. The answer counts what happened: `drops_recorded`, `items_proposed`, `timers_updated`,
`duplicates`, `invalid`...

**/addons/ledger** shows recent imports per member and how to set up the companion. The companion's
README explains install and use step by step, and exactly which parts of the Ledger format are uncertain.

## Claude Integration (MCP server)

An [MCP](https://modelcontextprotocol.io) server that lets Claude Code or Claude Desktop use the hall. It's
a thin client over the hall's JSON API and never opens the database, so **Claude has exactly the
permissions of the member whose token it uses**.

Setup (also shown on **/addons/claude**):

1. Create a personal API token on your profile page.
2. Claude Code:

   ```bash
   claude mcp add hallkeeper -e MMGU_API_URL=https://hall.example.org -e MMGU_API_TOKEN=mmgu_... \
     -- uvx --from "mmgu[mcp] @ git+https://github.com/kevroy314/mmgu" mmgu mcp
   ```

   Claude Desktop (`claude_desktop_config.json`):

   ```json
   {"mcpServers": {"hallkeeper": {
     "command": "uvx",
     "args": ["--from", "mmgu[mcp] @ git+https://github.com/kevroy314/mmgu", "mmgu", "mcp"],
     "env": {"MMGU_API_URL": "https://hall.example.org", "MMGU_API_TOKEN": "mmgu_..."}}}}
   ```

   If Hallkeeper is installed (`pip install "mmgu[mcp]"`), the command is just `mmgu mcp`.

3. For clients that want a URL instead of a command, run it as streamable HTTP on your own machine:
   `python -m mmgu.addons.mcp_server.server --http --port 8765` and connect to
   `http://127.0.0.1:8765/mcp`. It still uses the one token from the environment, so don't expose that
   port to anyone else.

Tools: `search_items`, `get_item`, `report_drop`, `roster`, `vault_holdings`, `vault_requests`,
`board_listings`, `board_requests`, `post_board_request`, `who_can_craft`, `upcoming_events`,
`spawn_timers`, `report_tod`, `list_proposals`, `propose_change`. The writes are only things the member
could do in the web app themselves. **`propose_change` is the only way Claude suggests anything else**: it
files a suggestion that an officer approves or discards in the web app. Tools for modules that are off
answer "that part of the hall is closed".

## Writing your own add-on

An add-on is an ordinary Hallkeeper module with `kind="addon"`. Put it in its own Python package and
register it through the `mmgu.modules` entry point group:

```toml
# pyproject.toml of your package
[project.entry-points."mmgu.modules"]
stables = "hallkeeper_stables.module:MODULE"
```

```python
# hallkeeper_stables/module.py
from mmgu.core.modules import Module, NavItem, SettingField
from mmgu.core.permissions import Permission


def _router():
    from hallkeeper_stables.routes import router
    return router


def _setup(hall):
    from hallkeeper_stables import hooks
    hooks.register(hall)          # hall.ext.add(...), hall.bus.subscribe(...)


MODULE = Module(
    id="stables",                 # also the prefix of your tables: stables_mounts, ...
    name="The Stables",           # the in-world name
    plain_name="Mount tracker",   # what it actually is
    description="Who has which mount, and where to get one.",
    kind="addon",
    default_enabled=False,
    tos_risk="none",              # "caution" or "high" if it reads game output; then write tos_notice
    tos_notice="",                # 2-4 plain sentences shown on the enable card
    requires=["roster"],
    nav=[NavItem("The Stables", "Mount tracker", "/stables", icon="flag", permission="stables.view")],
    permissions=[Permission("stables.view", "See the Stables", "recruit", module="stables")],
    settings=[SettingField("max_mounts", "Mounts per character", "int", 3)],
    router=_router,
    setup=_setup,
)
```

Useful `Module` fields: `nav` (rail links; skip for admin-only pages, which leaders reach from the
Steward's Office), `permissions` (each names the lowest rank and any duties that grant it; leaders can
override), `settings` (edited in Steward's Office → Settings, read with `hall.setting("stables", "key")`;
type `secret` never shows the stored value), `jobs` (run every N seconds), `channels` (Discord channels a
leader picks), `bot_setup` (slash commands). Templates go in `templates/<id>/`, CSS in `static/*.css`
(loaded automatically), models in `models.py` (subclass `mmgu.db.Base`).

Extension slots let an add-on contribute to other modules' pages without editing them
(`hall.ext.add(slot, fn, module="stables", order=100)`):

| Slot | Signature |
|---|---|
| `item.panels` | `async fn(request, session, item) -> str \| None` (HTML on an item page) |
| `item.discord_fields` | `async fn(session, item) -> list[tuple[str, str]]` |
| `member.panels` | `async fn(request, session, member) -> str \| None` |
| `hall.cards` | `async fn(request, session) -> str \| None` (dashboard card; check permissions) |
| `search.providers` | `async fn(session, q, viewer) -> list[SearchHit]` |
| `archive.readers` | `async fn(image: bytes) -> ReaderResult \| None` (see `mmgu.modules.archive.reading`) |
| `vault.readers` | `async fn(image: bytes) -> list[{"name": str, "qty": int}] \| None` |

Contributions from add-ons that are off are skipped automatically. House rules: every write goes through a
service function that calls `mmgu.core.audit.record(...)` and emits a bus event; anything a machine
produces becomes a `Proposal` for a person to approve; and if the add-on reads game output, say so plainly
in `tos_notice`.
